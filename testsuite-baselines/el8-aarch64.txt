# Known testsuite failures for the el8 / aarch64 toolchain (gcc 14.2.1).
#
# Only one entry is stable, so this file is NOT used as a strict gate for
# aarch64 — see the note on flakiness below. It is kept as the record of what
# is genuinely broken versus what the emulator invents.

# A real baseline limit, reproduced on every run: GCC 14's heap trampolines
# (-ftrampoline-impl=heap) call __builtin_nested_func_ptr_created, which lives
# in libgcc_s at version GCC_14.0.0. The el8 baseline libgcc_s (GCC 8.5) tops
# out at GCC_7.0.0, so the feature cannot work on this baseline at all.
# `crossforge audit` reaches the same verdict statically, without running it:
#   ERROR [symbol-version] requires libgcc_s.so.1@GCC_14.0.0 but the baseline
#   libgcc_s.so.1 does not provide it
gcc.dg/heap-trampoline-1.c execution test

# --- Not stable ------------------------------------------------------------
# Every other aarch64 failure seen so far is an *execution* test, and the set
# changes between runs of the identical suite. Two consecutive dg.exp runs
# (2026-08-27, 8 jobs):
#   run 1: atomic-exchange-2
#   run 2: bitint-38, c23-float-1, pr107385, utf32-1  (atomic-exchange-2 passed)
# Each of them also passes when run on its own. That is user-mode qemu under
# parallel load, not code generation — so a set-based gate would report
# regressions that are not there. aarch64 therefore uses a count threshold
# with headroom in the weekly run, and stays out of the per-commit gate.
#
# The way out is executing the target tests on real hardware (a DejaGnu remote
# board pointed at an arm64 runner) rather than emulating them.
